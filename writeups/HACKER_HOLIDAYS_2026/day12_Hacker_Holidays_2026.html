3 WMI Persistence — A Primer

To understand this room, you need to understand how WMI-based persistence differs from traditional methods.

Traditional persistence (e.g. Registry Run key):

Computer starts
→
Registry Run key
→
Malicious program starts

WMI persistence:

Windows starts
→
WMI service running
→
Event subscription waits
→
Condition occurs
→
WMI launches payload
→
Malicious code executes

The three critical WMI components that form a persistence subscription:

  1. __EventFilter — defines what event triggers execution
  2. Event Consumer (e.g. CommandLineEventConsumer) — defines what to execute
  3. __FilterToConsumerBinding — ties the filter and consumer together

4 Examining OBJECTS.DATA

Using strings and a WMI repository parser against OBJECTS.DATA, several suspicious entries emerge.

4.1 The Event Filter — EngineTelemetryFilter

Extracted Filter Query 
SELECT * FROM __InstanceModificationEvent
WITHIN 60
WHERE TargetInstance ISA 'Win32_LocalTime'
AND TargetInstance.Minute = 30

Translation for beginners:

  • __InstanceModificationEvent — monitor for changes to any WMI object
  • WITHIN 60 — poll approximately every 60 seconds
  • Win32_LocalTime — the object being watched is Windows' local time
  • Minute = 30 — trigger when the minute value hits 30
What this means: Every ~60 seconds, Windows checks the local time. If the current minute is 30 (e.g. 14:30, 15:30, 16:30...), the consumer fires. This is a time-based WMI persistence trigger — the attacker gets code execution once per hour, every hour, indefinitely.

5 The Consumer — EngineTelemetryConsumer

Alongside the filter, we find a CommandLineEventConsumer named EngineTelemetryConsumer. Its command property contains:

Consumer Command (truncated for readability) 
cmd /C powershell.exe -Sta -Nop -Window Hidden -enc <BASE64_BLOB>

Breakdown of the PowerShell flags:

Flag Meaning Forensic Significance
-Sta Single-Threaded Apartment Not inherently malicious; common in scripting
-Nop No Profile Prevents normal PowerShell profile from loading — avoids logging
-Window Hidden Hide the PowerShell window 🚩 Highly suspicious — user never sees the execution
-enc Base64-encoded command 🚩 Major red flag — classic obfuscation technique
Execution chain so far: WMI → time trigger (Minute=30) → CommandLineEventConsumer → cmd.exe → hidden PowerShell → Base64-encoded script

6 Decoding Layer 1 — The PowerShell Script

Base64 is encoding, not encryption. We decode the -enc blob to reveal the PowerShell logic:

Decoded PowerShell 
$file = ([WmiClass]'ROOT\cimv2:Win32_HardwareTelemetry').Properties['ConfigData'].Value;
$o = New-Object IO.MemoryStream;
$d = New-Object IO.Compression.DeflateStream(
    [IO.MemoryStream][Convert]::FromBase64String($file),
    [IO.Compression.CompressionMode]::Decompress
);
$d.CopyTo($o);
[Reflection.Assembly]::Load($o.ToArray()).EntryPoint.Invoke($null);

What this script does, step by step:

  1. Retrieves the ConfigData property from a custom WMI class called Win32_HardwareTelemetry
  2. Base64-decodes that data
  3. Decompresses it using Deflate (the same compression used in ZIP files)
  4. Loads the resulting bytes directly into memory as a .NET assembly
  5. Invokes the assembly's EntryPoint — executing the malicious payload
Key takeaway: The attacker never writes a malicious .exe to disk. The payload lives entirely within the WMI repository as Base64-encoded, Deflate-compressed data. At runtime, it's reconstructed in memory and executed via Reflection.Assembly.Load() — a classic fileless / in-memory execution technique.

10 Why This Evades Standard Tools

The room's hint from @0xMia warns that "usual autoruns/persistence tools straight up don't catch this one." Here's why:

Evasion Technique How It Works Here
Masquerading Filter and consumer named EngineTelemetry* — sounds like a legitimate Microsoft component
WMI as storage Payload lives as a property value inside the WMI repository — no suspicious files on disk
In-memory execution Reflection.Assembly.Load() loads the .NET payload directly into memory — never touches disk as an .exe
Encoding + Compression Base64 + Deflate obfuscate the payload — static signature scanners won't match
No traditional persistence artifact No registry Run key, no Scheduled Task, no Startup folder entry — Autoruns won't find it

12 Lessons Learned

For Beginners — A Mental Model for Persistence Forensics

Three questions to always ask:

  1. Persistence: How does the attacker make their code run again after reboot or logoff?
  2. Forensics: What evidence would that mechanism leave behind?
  3. Reverse Engineering: What does the suspicious program actually do?

Don't Trust Names

EngineTelemetryFilter and EngineTelemetryConsumer sound legitimate. That's intentional. Always examine what an object triggers, what it executes, and where its payload comes from — not what it calls itself.

Base64 ≠ Encryption

Base64 is reversible encoding. When you see -enc in a PowerShell command, the first thing you should do is decode it. Attackers use it for obfuscation, not confidentiality.

Fileless ≠ Invisible

In-memory execution via Reflection.Assembly.Load() avoids writing to disk, but it still leaves traces: WMI repository artifacts, PowerShell script block logs, process creation events, and (in this case) the user account itself.
