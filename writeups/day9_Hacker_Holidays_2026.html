1 Reconnaissance — Inspecting the Kiosk

We're given a single target URL pointing to an Azure Blob Storage static website:

Target
https://cryptocabanaf5scjagc.z13.web.core.windows.net/

The landing page is a simple seed phrase backup kiosk for the CryptoCabana resort app. It invites you to paste a recovery phrase and promises — in exactly four words — "Backed up. Sleep easy."

Before clicking anything, the first rule of web challenges applies: always check the page source. Open your browser's Developer Tools (F12) and look at the Sources tab, or simply view the page source with Ctrl+U.

Right there in app.js, the kiosk hands out its most valuable possession for free — a Shared Access Signature (SAS) token embedded directly in client-side JavaScript:

app.js — Leaked Credentials
const STORAGE_ACCOUNT = "{REDACTED}";
const BACKUPS_CONTAINER = "backups";
const BACKUP_SAS = "{REDACTED}";
💡 What is a SAS token? A Shared Access Signature is a signed URL that grants access to Azure Storage resources without needing the account key. Think of it as a temporary, scoped password. The problem here is that it's embedded in client-side code — visible to anyone who visits the page.

Let's decode what this SAS token actually grants. The parameters tell the whole story:

Parameter Value Meaning
sp rl Permissions: Read and List
srt sco Scope: Service, Container, and Object level — not limited to just one container
ss b Service: Blob storage only
se 2099-12-31 Expires in 2099 — effectively forever
🔑 The critical mistake: srt=sco means this SAS token works at the entire storage account level, not just the backups container. The kiosk only uses it to upload to backups, but we can use it to list and read from every container in the storage account.

The note from IT is particularly ironic: "Rotate this if it ever leaves the vault." — and yet here it is, sitting in blob storage protected only by a SAS token that was handed out freely in client-side JavaScript.

3 Authenticating as the Service Principal

Now we use the stolen credentials to authenticate to Azure as the backup automation service principal. This account has permissions to access the Key Vault referenced in the JSON file.

Azure CLI — Login as Service Principal
az login --service-principal \
  --username {REDACTED} \
  --password "{REDACTED}" \
  --tenant {REDACTED}
[ { "cloudName": "AzureCloud", "id": "{REDACTED}", "isDefault": true, "name": "Az-Subs-CTF", "tenantId": "{REDACTED}", "user": { "name": "{REDACTED}", "type": "servicePrincipal" } } ]

We're in. The service principal has access to the subscription Az-Subs-CTF, which contains the Key Vault we found referenced earlier.

💡 What is a service principal? Think of it as a "robot account" — an identity used by applications and automation scripts to access Azure resources. It has its own permissions separate from human user accounts. This one was created by IT to let the backup automation access the Key Vault.

🚩 The problem: Shards 1 and 3 give us the beginning and end of the flag — THM{n0t_ur and ur_c01ns!} — but shard-2 has been rotated. Its current value is a note from IT, not the actual flag piece. The itinerary warned us: "a vault that won't give up the real values on the first ask."

Notice the hint embedded in the rotated value itself: "old value should still be recoverable if you know where to look." We also try the master-key but the service principal lacks permissions to read it. That's fine — the three shards are what we need.

5 Recovering the Rotated Secret

The key insight here is that Azure Key Vault secrets support versioning. When a secret is "rotated," a new version is created, but the old version still exists — you just need to ask for it explicitly by its version ID.

@0xMia's story hinted at this perfectly: "if a value looks freshly rotated, ask yourself what it looked like five minutes before that."

Let's list all versions of key-shard-2 with their metadata to find the older one:

Azure CLI — List All Versions with Details
az keyvault secret list-versions \
  --vault-name ccabana-kv-f5scjagc \
  --name key-shard-2 \
  --maxresults 25 \
  --query "[].{Version:version, Created:attributes.created, Updated:attributes.updated, Enabled:attributes.enabled}" \
  --output table
Version Created Updated Enabled ------------------------------------ ----------------------- ----------------------- --------- a1b2c3d4e5f6... (current) 2026-07-19T15:20:00+00 2026-07-19T15:20:00+00 True 3d6492d2c6f74123bc754a9ded22b2a0 2026-07-16T18:26:00+00 2026-07-16T18:26:00+00 True

There it is — the older version with ID 3d6492d2c6f74123bc754a9ded22b2a0 from three days before the rotation. Let's retrieve its value:

Azure CLI — Read the Old Version
az keyvault secret show \
  --vault-name ccabana-kv-f5scjagc \
  --name key-shard-2 \
  --version "3d6492d2c6f74123bc754a9ded22b2a0" \
  --query value \
  --output tsv
_k3ys_n0t_
🎯 Found it! The old version of key-shard-2 held the middle piece of the flag. Even though IT rotated the secret to hide it, the version history preserved the original value.

6 Assembling the Flag

We now have all three pieces:

Combine them in order to reveal the full flag — a classic piece of crypto wisdom rendered in leetspeak:

THM{REDACTED_BUT_YOU_HAVE_ALL_THE_PIECES}

"Not your keys, not your coins" — the foundational mantra of self-custody in cryptocurrency. Rather fitting for a challenge about a seed phrase backup kiosk that leaked everything it was supposed to protect.

🛡️ Remediation — What Went Wrong

This challenge illustrates a cascade of security failures, each one enabling the next:

# Issue What Happened How to Fix It
1 SAS Token in Client-Side Code The SAS token was embedded in app.js, visible to anyone who views the page source Never expose SAS tokens in frontend code. Use a backend API that authenticates users before generating short-lived, least-privilege tokens
2 Overly Permissive SAS Scope srt=sco granted Service, Container, and Object access — allowing enumeration of all containers, not just backups Scope SAS tokens to the minimum required container. Use srt=o (Object only) with a specific container path if possible
3 No Expiry on SAS Token The SAS token expires in 2099 — essentially permanent Set short-lived SAS tokens (hours or days, not decades) and rotate them regularly
4 Credentials Stored in Blob Storage Full service principal credentials with Key Vault access were stored as JSON in a blob Never store credentials in blob storage. Use Managed Identities for Azure services that need to authenticate to each other
5 Secret Rotation Without Cleanup IT rotated the secret but the old version remained accessible in the version history When rotating secrets that contain sensitive data, either purge old versions or ensure they're disabled and access-controlled
6 Service Principal Over-Permissioned The backup automation account had read access to all secrets in the Key Vault, not just the ones it needed Follow the principle of least privilege. Grant access to specific secrets only, not the entire vault
🔗 The kill chain: SAS token in JS → Container enumeration → Discovery of vault container → Credential JSON download → Service principal login → Key Vault access → Secret version enumeration → Old flag shard recovery. Each step relied on the previous misconfiguration. Breaking any single link would have stopped the attack.
